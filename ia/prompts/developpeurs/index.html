Prompts ChatGPT pour les développeurs

Dix prompts pour comprendre du code, trouver un bug, écrire des tests et documenter, tout en gardant la main sur le résultat.

L'essentiel

  1. Expliquer un bout de code
  2. Trouver la cause d'un bug
  3. Écrire des tests unitaires
  4. Refactorer sans changer le comportement
  5. Relire une pull request
  6. Rédiger une documentation
  7. Optimiser une requête SQL
  8. Concevoir une architecture simple
  9. Convertir du code d'un langage à un autre
  10. Expliquer une erreur de sécurité

Une IA est utile pour expliquer du code inconnu, proposer des tests et relire une fonction. Elle l'est moins quand on lui demande de tout écrire sans contexte : le code produit peut sembler correct et ne pas l'être.

Donnez toujours le langage, les versions, le contexte et le résultat attendu. Collez un extrait minimal plutôt que tout le projet.

  • Indiquez le message d'erreur exact et ce que vous avez déjà essayé.
  • Relisez et testez tout code généré.
  • Ne collez jamais de secrets : clés d'API, mots de passe, jetons.

Remplacez les passages entre [crochets] par vos informations, puis collez le prompt dans ChatGPT, Claude, Gemini, Copilot ou Le Chat. Pour adapter un prompt, utilisez le générateur de prompt.

1. Expliquer un bout de code

Pour comprendre une fonction que vous n'avez pas écrite.

Tu es développeur senior en [langage]. Explique le code suivant à un développeur de niveau [débutant/intermédiaire] : [collez le code]
Format : résumé en une phrase, explication ligne par ligne des parties importantes, complexité approximative, deux risques ou cas limites. Si le contexte te manque pour être certain d'un point, dis-le au lieu de supposer.

2. Trouver la cause d'un bug

Quand une erreur résiste à vos premières pistes.

Je rencontre un bug en [langage, framework, version]. Comportement attendu : [description]. Comportement observé : [description].
Message d'erreur exact : [collez l'erreur]. Code concerné : [extrait minimal]. Ce que j'ai déjà essayé : [liste].
Propose les 3 causes les plus probables, classées, et pour chacune comment la vérifier. Ne réécris pas tout : donne d'abord les vérifications à faire.

3. Écrire des tests unitaires

Pour couvrir une fonction avec des cas utiles.

Écris des tests unitaires avec [framework de test] pour la fonction suivante : [collez la fonction]
Couvre le cas nominal, les cas limites (valeurs vides, extrêmes, types inattendus) et les erreurs. Nomme chaque test de façon explicite. Après les tests, liste les comportements que la fonction ne gère pas et que je devrais décider de traiter.

4. Refactorer sans changer le comportement

Pour clarifier une fonction longue ou confuse.

Voici une fonction en [langage] qui fonctionne mais qui est difficile à lire : [collez le code]
Propose un refactoring qui conserve exactement le comportement : noms plus clairs, découpage en petites fonctions, suppression de la duplication. Explique chaque changement en une phrase. Indique les tests à lancer pour vérifier que rien n'a changé.

5. Relire une pull request

Pour obtenir un second regard avant la relecture humaine.

Tu es relecteur de code exigeant. Voici un diff en [langage] : [collez le diff]
Analyse-le selon : exactitude, sécurité (injections, gestion des entrées, secrets), performance, lisibilité, tests manquants. Classe les remarques par gravité : bloquant, important, détail. Indique la ligne concernée pour chaque remarque.

6. Rédiger une documentation

Pour documenter un module ou une API.

Rédige la documentation du module suivant pour des développeurs de l'équipe : [collez le code ou la description]
Plan : objectif, installation, exemple d'utilisation minimal, description des fonctions principales (paramètres, retours, erreurs), limites connues. Format Markdown. N'invente aucun comportement : si une information manque, mets un point d'interrogation à vérifier.

7. Optimiser une requête SQL

Pour comprendre pourquoi une requête est lente.

Voici une requête SQL pour [moteur et version] : [collez la requête]
Structure des tables (colonnes et index) : [description]. Volume : [ordre de grandeur]. Plan d'exécution : [collez-le si disponible].
Explique pourquoi elle peut être lente, propose une version optimisée et les index à envisager, et indique comment mesurer le gain avant de déployer.

8. Concevoir une architecture simple

Pour comparer des options avant de coder.

Je dois concevoir [fonctionnalité ou service]. Contraintes : [équipe, délai, volumétrie, technologies imposées].
Propose deux architectures de complexité différente, avec avantages, inconvénients, risques et coût de maintenance. Termine par une recommandation justifiée. Pose-moi d'abord les questions dont tu as besoin pour éviter une réponse trop générale.

9. Convertir du code d'un langage à un autre

Pour migrer un script en gardant le sens.

Convertis le code suivant de [langage source] en [langage cible] : [collez le code]
Utilise les conventions idiomatiques du langage cible. Liste les différences de comportement possibles (types, arrondis, gestion des erreurs, dates). Signale les fonctions ou bibliothèques sans équivalent direct. Propose 3 cas de test à comparer entre les deux versions.

10. Expliquer une erreur de sécurité

Pour comprendre une alerte d'audit ou d'analyseur.

Un outil d'analyse signale ceci dans mon projet en [langage, framework] : [collez l'alerte, sans secrets].
Explique en termes simples le risque, comment un attaquant pourrait l'exploiter, et propose une correction avec un extrait de code. Indique comment vérifier que la faille est bien corrigée et si d'autres endroits du code peuvent être concernés.

Relire et tester le code généré

Un code qui compile n'est pas forcément correct. L'IA peut inventer une fonction qui n'existe pas dans votre version de bibliothèque, oublier un cas limite ou introduire une faille. Relisez, exécutez, testez avant d'intégrer, comme pour le code d'un collègue.

Ne collez jamais de secrets

Retirez avant tout envoi : clés d'API, mots de passe, jetons, chaînes de connexion, certificats, adresses internes et données de clients. Remplacez-les par des valeurs fictives. Si un secret a été collé par erreur, considérez-le comme compromis et changez-le.

Code propriétaire et licences

Vérifiez la politique de votre entreprise avant de transmettre du code propriétaire à un service externe. Pour du code généré, restez attentif aux licences des bibliothèques proposées.

Limites

L'IA ne voit pas votre projet entier ni votre environnement. Indiquez toujours les versions, et préférez de petites demandes précises à une demande vague. Vérifiez la documentation officielle quand une API vous paraît douteuse.

Questions fréquentes

Puis-je coller le code de mon entreprise dans ChatGPT ?

Cela dépend de la politique de votre entreprise et des conditions de l'outil. Beaucoup interdisent d'envoyer du code propriétaire à un service grand public. Renseignez-vous auprès de votre responsable sécurité avant tout usage.

Comment éviter que l'IA invente des fonctions ?

Indiquez la version de la bibliothèque, demandez-lui de signaler ses incertitudes et vérifiez dans la documentation officielle. Exécutez toujours le code : une fonction inexistante provoque en général une erreur immédiate.

L'IA peut-elle écrire une application entière ?

Elle peut produire un prototype, mais la maintenance, la sécurité et les cas limites demandent votre expertise. Travaillez par petites étapes, testez chaque partie et gardez la compréhension de l'ensemble.
